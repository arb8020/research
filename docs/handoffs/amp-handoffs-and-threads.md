## Threads

### Thread ID format

`T-<uuid>` (e.g., `T-a1b2c3d4-e5f6-...`).

Generated by `SQ()`:
```js
function SQ() {
  return `T-${crypto.randomUUID()}`;
}
```

Validated by `U3()` which checks the `T-` prefix + UUID regex.

### Thread data model

Inferred from usage throughout the bundle:

- `id: string` -- the `T-xxx` ID
- `messages: Message[]` -- the conversation
- `title: string | undefined`
- `agentMode: string | undefined` -- e.g., "smart", "code"
- `created: number` -- timestamp
- `env: { initial: ThreadEnvironment }` -- workspace trees, platform info
- `relationships: Relationship[]` -- links to parent/child threads
- `mainThreadID: string | undefined` -- set for subagent threads
- `v: number` -- version counter, incremented on mutation
- `queuedMessages` -- pending messages
- `activatedSkills` -- skills loaded in thread
- `todos` -- the todo list state

### Message roles

`user`, `assistant`, `info`

**user messages** contain:
- `content` -- text/image/tool_result blocks
- `source` -- where the message came from
- `fileMentions` -- resolved `@path` references
- `userState` -- editor state (cursor, visible files)
- `agentMode`
- `discoveredGuidanceFiles` -- AGENTS.md-style files

**assistant messages** contain:
- `content` -- text/thinking/redacted_thinking/tool_use blocks
- `state` -- `{ type: "streaming" | "complete" | "cancelled" | "error", stopReason?: "end_turn" | "tool_use" | "refusal" }`
- `usage` -- token counts

**info messages** contain:
- summaries (for context compaction)
- manual bash invocations
- skill injection prompts

### Storage

Threads sync to ampcode.com via `threadSyncService`. Locally:

- `threadService` provides `exclusiveSyncReadWriter` (read/write lock per thread)
- `threadStorage` for raw persistence
- `threadService.observe(id)` for reactive updates (RxJS Observable)

The `ThreadReadWriter` wraps reads/writes with a version-based patch system using JSON Patch (RFC 6902). This enables real-time sync.

### Thread mutations (delta types)

All mutations are dispatched as typed deltas:

- `user:message`, `assistant:message`, `assistant:message-update`
- `tool:data`, `tool:processed`
- `thread:truncate`, `title`, `agent-mode`
- `relationship`, `environment`
- `cancelled`, `inference:completed`
- `course-correction`, `course-correction:usage-only`
- `fork:created`, `draft`, `setPendingNavigation`
- `user:message-queue:enqueue`, `user:message-queue:dequeue`
- `user:tool-input`
- `pending-skills`
- `info:manual-bash-invocation`

## Relationships

Threads link to each other via a `relationships` array. Each relationship:

```ts
interface Relationship {
  threadID: string;       // the related thread
  type: "handoff" | "mention" | "fork";
  role: "parent" | "child";
  messageIndex: number;   // which message triggered the relationship
  createdAt: number;      // timestamp
  comment?: string;       // for handoffs, this is the goal
}
```

When a handoff creates thread B from thread A:
- Thread A gets: `{ threadID: B, type: "handoff", role: "parent", messageIndex: N }`
- Thread B gets: `{ threadID: A, type: "handoff", role: "child", messageIndex: N }`

**Mentions** (`@@thread-id`) are detected by scanning assistant tool_use blocks for the `read_thread` tool. These create implicit `type: "mention"` relationships (computed on read, not stored).

## Handoff: the full mechanism

### 1. Tool definition (agent-initiated handoff)

The agent sees a tool called `handoff` with this schema:

```json
{
  "type": "object",
  "properties": {
    "goal": {
      "type": "string",
      "description": "A short description of the next task to accomplish in the new thread. Should be a single sentence or at most one paragraph. Focus on what needs to be done next, not what was already completed."
    },
    "follow": {
      "type": "boolean",
      "default": false,
      "description": "If true, navigate to the new thread after creation. Use this when the current thread is stopping and work should continue in the new thread."
    }
  },
  "required": ["goal", "follow"]
}
```

Tool description:

> Hand off work to a new thread that runs in the background. Use this tool when you need to continue work in a fresh context because:
> - The current thread is getting too long and context is degrading
> - You want to start a new focused task while preserving context from the current thread
> - The current thread's context window is near capacity
>
> When you call this tool:
> 1. A new thread will be created with relevant context from this thread
> 2. The new thread will start running in the background
> 3. The current thread continues to run -- you can finish up any remaining work
>
> When the user message tells you to continue the work or to handoff to only one new thread, you should follow to the new thread by setting follow to true.

### 2. Context extraction (`createHandoffPrompt`, internally `lb`)

This is the core of handoff. Here's exactly what happens:

#### Step 1: Clean the thread

`cleanThreadForHandoff` (internally `In0`) removes trailing incomplete tool_use sequences. If the last assistant message has `stopReason: "tool_use"` but the corresponding tool_results don't exist yet, strip both the assistant message and the incomplete user message. Repeat until clean.

#### Step 2: Truncate for token savings

`W11()` strips `fileMentions` from user messages and truncates tool results longer than 2000 chars, appending:
```
[ ... omitted remaining lines to make summarizing use less tokens ... ]
```

Truncation targets the fields: `text`, `diff`, `output`.

#### Step 3: Check token budget

If the thread's `totalInputTokens >= contextWindow - maxOutputTokens`, fall back to `vertexai/gemini-2.5-flash` instead of the current model. This prevents the extraction call itself from exceeding context.

#### Step 4: Call the LLM with `create_handoff_context` tool

This is a single forced tool-call to extract context. The user prompt sent to the model:

```
Extract relevant context from the conversation above for continuing
this work. Write from my perspective (first person: "I did...",
"I told you...").

Focus on capabilities and behavior, not file-by-file changes.
Avoid excessive implementation details (variable names, storage keys,
constants) unless critical.

Format: Plain text with bullets. No markdown headers, no bold/italic,
no code fences. Use workspace-relative paths for files.

My request:
{goal}

Use the create_handoff_context tool to extract relevant information and files.
```

The tool schema forces the LLM to return:

```json
{
  "relevantInformation": "string -- first-person context extraction with bullets",
  "relevantFiles": ["string[] -- max 10 workspace-relative paths, most important first"]
}
```

The `relevantInformation` field instructions:

> Extract relevant context from the conversation. Write from first person perspective ("I did...", "I told you...").
>
> Consider what's useful based on the user's request. Questions that might be relevant: What did I just do or implement? What instructions did I already give you which are still relevant (e.g. follow patterns in the codebase)? Did I provide a plan or spec that should be included? What did I already tell you that's important (certain libraries, patterns, constraints, preferences)? What important technical details did I discover (APIs, methods, patterns)? What caveats, limitations, or open questions did I find? What files did I tell you to edit that I should continue working on?
>
> Extract what matters for the specific request. Don't answer questions that aren't relevant. Pick an appropriate length based on the complexity of the request.

This call is made with `tool_choice: { type: "tool", name: "create_handoff_context" }` (forced). The model sees the full cleaned+truncated thread as conversation history, plus the extraction prompt as the final user message.

For Anthropic models, it also sets `temperature: 0.1` and passes appropriate beta headers.

#### Step 5: Resolve file URIs

- Parse `@mentions` from the goal text
- Take the LLM's `relevantFiles` array
- Resolve both against workspace roots
- Cap at 10 files total
- `@mentions` from the goal get priority (listed first)

#### Step 6: Budget file inclusion by tokens

Each file's size is estimated as: `ceil(min(fileSize, 32768) / 3.5)` tokens.

Files are included (as `@` mentions) up to a **25,000 token budget**. Files that don't fit are listed as plain paths in a separate line.

#### Step 7: Assemble the handoff prompt

The final message for the new thread:

```
Continuing work from thread {threadID}. When you lack specific
information you can use read_thread to get it.

@file1 @file2 @file3 ...

Other relevant files: path/a, path/b

{relevantInformation from the LLM extraction}

{goal}
```

The `@file` mentions get resolved into actual file content when the new thread processes its first user message (via the file mention resolution pipeline).

### 3. New thread creation (`startNewThread`)

```js
startNewThread(deps, {
  agentMode: parentThread.agentMode,  // inherit agent mode
  parent: {
    threadID: parentThread.id,
    type: "handoff",
    messageIndex: parentThread.messages.length - 1,
    comment: goal
  },
  initialMessage: handoffPrompt,      // from step 2
  navigate: follow                     // from tool input
})
```

This:
1. Generates a new thread ID via `SQ()` (`T-<uuid>`)
2. Creates a `ThreadWorker` for it
3. Calls `worker.resume()` to initialize
4. If `agentMode` is set, dispatches `agent-mode` delta
5. Writes `relationship` deltas to **both** parent and child threads
6. Sends `initialMessage` as a `user:message` delta
7. If `navigate: true` and parent exists, sets pending navigation on the parent worker

The new thread immediately starts inference -- the agent sees the extracted context as its first user message and begins working.

### 4. Tool execution flow

The handoff tool function (`f68`) is an RxJS Observable:

1. Emits `{ status: "in-progress" }`
2. Calls `createHandoffPrompt()` (the `lb` function)
3. Calls `startNewThread()` on the `ThreadWorkerService` singleton (`O4`)
4. Emits `{ status: "done", result: { newThreadID, message } }`
5. Has a 30-second timeout (`Lj1 = 30000`) -- aborts if exceeded
6. Supports cancellation via returned teardown function

### 5. Handoff from `ThreadWorker.executeHandoff()`

The `ThreadWorker` class also has an `executeHandoff` method (used by hooks):

```js
async executeHandoff(goal) {
  this.handoffState.next({ goal });
  const handoffPrompt = await createHandoffPrompt(
    this.thread, goal, [], this.deps.configService,
    new AbortController().signal, this.fs.fileSystemReader()
  );
  const { threadID } = await threadWorkerService.startNewThread(this.deps, {
    agentMode: this.thread.agentMode,
    parent: { threadID: this.threadID, type: "handoff", ... },
    initialMessage: handoffPrompt
  });
  this.handoffState.next({ goal, result: { newThreadID } });
}
```

### 6. CLI-initiated handoff (`amp threads handoff`)

```bash
amp threads handoff T-xxx --goal "Continue the auth work"
echo "Continue the auth work" | amp threads handoff T-xxx
amp threads handoff --goal "Fix the remaining tests"  # uses last thread
```

The CLI function (`KP8`):
1. Resolves thread ID (argument or last thread via `r51`)
2. Loads the thread via `threadService.get()`
3. Reads goal from `--goal` flag or stdin
4. Calls `createHandoffPrompt()` directly (same `lb` function)
5. Calls `startNewThread()` with same parameters as the tool
6. Uploads both threads to ampcode.com via `threadSyncService`
7. Either opens the TUI on the new thread (default) or prints the thread ID (`--print`)

## ThreadWorker architecture

Each active thread gets a `ThreadWorker` instance, managed by a singleton `ThreadWorkerService` (`O4`). The worker handles:

- **Inference loop**: calls the LLM, streams responses, handles retries with exponential backoff (5s base, 60s max, 5 max auto-retries)
- **Tool orchestration**: `ToolOrchestrator` manages parallel/sequential tool execution based on resource key conflicts
- **File change tracking**: append-only backup system with atomic revert per tool_use
- **Course correction**: a separate Gemini model watches the conversation and intervenes when the agent goes off track (currently gated to specific emails)
- **Handoff state**: exposed as an RxJS observable for UI updates
- **Retry/error handling**: ephemeral errors with countdown timers
- **Hooks**: pre/post tool execution hooks, assistant end-turn hooks

The `ThreadWorkerService` caps at ~25 concurrent workers before logging warnings.

## Key design decisions for reimplementation

**Handoff is a single forced tool call, not a sub-agent.** The context extraction is one LLM inference with `tool_choice: forced`. No iterative file reading. Fast and predictable.

**The new thread gets file content via `@mentions`, not inline.** The handoff prompt uses `@path/to/file` syntax. When the new thread's first user message is processed, file mention resolution reads those files from disk and attaches them. This keeps the handoff prompt itself small.

**`read_thread` is a fallback.** The handoff prompt tells the agent "when you lack specific information you can use read_thread to get it." This tool lets the new thread's agent read messages from the parent thread on-demand, without including everything upfront.

**Relationships are bidirectional.** Both parent and child record the link. This enables the "thread map" visualization showing hub-and-spoke and chain patterns.

**Thread versioning uses JSON Patch.** Mutations are diffed and synced as RFC 6902 patches via `exclusiveSyncReadWriter`. This enables real-time sync to ampcode.com.

**30-second timeout** on the handoff tool prevents hung handoffs from blocking the agent.

**Model fallback for large threads.** When the thread exceeds the model's context window, extraction falls back to `vertexai/gemini-2.5-flash` which has a larger context.

**First-person extraction prompt.** The "write from my perspective" instruction produces context that reads naturally as a user message in the new thread. The agent in the new thread sees it as instructions from the user, not a system summary.

**Token budget for files.** The 25K token budget and `ceil(min(size, 32768) / 3.5)` estimation prevents the handoff prompt from being too large for the new thread's first turn.

### `cleanThreadForHandoff` (`In0`)

Strips trailing incomplete tool_use sequences before extraction:

```js
// main.js:2298
function In0(J) {
  if (J.messages.length === 0) return J;
  return O2(J, (Q) => {
    let Y = true;
    while (Y && Q.messages.length > 0) {
      Y = false;
      let Z = Q.messages.length - 1,
        X = Q.messages[Z];

      // If last message is assistant with tool_use stop, remove it
      if (X?.role === 'assistant') {
        let G = X.state;
        if (G.type === 'complete' && G.stopReason === 'tool_use') {
          let K = new Set();
          for (let q of X.content)
            if (q.type === 'tool_use') K.add(q.id);
          if (K.size > 0) {
            Q.messages.pop();
            Y = true; // loop again
          }
        }
        continue;
      }

      // If last message is user with incomplete tool_results, remove both
      if (X?.role === 'user' && Z >= 1) {
        let G = Q.messages[Z - 1];
        if (G?.role === 'assistant') {
          let V = G.state;
          if (V.type === 'complete' && V.stopReason === 'tool_use') {
            let q = new Set();
            for (let z of G.content)
              if (z.type === 'tool_use') q.add(z.id);
            let W = new Set();
            for (let z of X.content)
              if (z.type === 'tool_result' && r5(z.run)) W.add(z.toolUseID);
            // If not all tool_uses have results, strip both messages
            if (!(q.size > 0 && [...q].every((z) => W.has(z)))) {
              Q.messages.pop(); // user
              Q.messages.pop(); // assistant
              Y = true;
            }
          }
        }
      }
    }
  });
}
```

### `createHandoffPrompt` (`lb`)

The main function that orchestrates context extraction:

```js
// main.js:2298 (Ww module)
async function lb(J, Q, Y, Z, X, G) {
  let V = performance.now(),
    K = In0(J),            // Step 1: clean incomplete tool_use
    q = W11(K),            // Step 2: truncate long results
    W = J.env?.initial;

  if (!W) throw Error('Thread environment not available for handoff');

  let H = {
    workspaceFolders: W.trees?.map((g) => g.uri).filter((g) => g !== void 0) ?? null,
    isWindows: W.platform?.os === 'windows',
  };

  // Step 3: Check if thread exceeds model context
  let z = await Z.getLatest(X),
    { model: F } = rJ(z.settings, J),
    U = i5(F),                              // get model info
    D = xJ(J),                              // get last usage
    B = U.contextWindow - U.maxOutputTokens,
    N;
  if (D && D.totalInputTokens >= B) {
    N = 'vertexai/gemini-2.5-flash';        // fallback for large threads
  }

  // Parse @mentions from goal text
  let w = Ho4(Q),
    M = H.workspaceFolders?.map((g) => Q0.parse(g)) ?? [];

  // Step 4: Call LLM with forced create_handoff_context tool
  let L = await Ao4({
    userGoal: Q,
    images: Y,
    thread: q,
    configService: Z,
    signal: X,
    modelOverride: N,
  });

  // Step 5: Resolve file paths
  let O;
  if (typeof L.relevantFiles === 'string')
    O = L.relevantFiles.split('\n').map((g) => g.trim()).filter(Boolean);
  else O = L.relevantFiles ?? [];

  // Resolve workspace-relative paths to URIs
  let A = [];
  for (let g of O) {
    let c = g.trim();
    if (!c) continue;
    if (c.startsWith('/') || /^[a-zA-Z]:[\\/]/.test(c)) continue; // skip absolute
    for (let h of M)
      try { A.push(P0(h.with({ path: `${h.path}/${c}` }))); break; } catch {}
  }

  // @mentions from goal get priority
  let I = [];
  for (let g of w)
    for (let c of M)
      try { I.push(P0(c.with({ path: `${c.path}/${g}` }))); break; } catch {}

  let k = [...new Set([...I, ...A])].slice(0, 10);  // cap at zo4=10

  // Step 6: Budget file inclusion by tokens
  let y = [],     // files to @mention
    S = [],       // files as plain paths (didn't fit budget)
    v = 0;        // estimated tokens used
  if (G) {
    let g = [];
    await Promise.all(
      k.map(async (i) => {
        try {
          let u = F7(i),
            V1 = await G.stat(u);
          if (!V1.isDirectory) {
            let M1 = s5(i, H);  // workspace-relative path
            g.push({
              uri: i,
              relativePath: M1,
              estimatedTokens: Do4(V1.size),  // ceil(min(size,32768)/3.5)
            });
          }
        } catch {}
      }),
    );
    let c = k.map((i) => g.find((u) => u.uri === i)).filter(Boolean),
      h = 25000;  // On0 = token budget
    for (let i of c)
      if (h >= i.estimatedTokens) {
        y.push(i.uri);
        h -= i.estimatedTokens;
        v += i.estimatedTokens;
      } else {
        S.push(i.relativePath);
```
