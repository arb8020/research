On Simplicity in SoftwareI keep talking about Simplicity, but it feels like a lot of people just don't understand what I'm talking about. No, Simplicity is not copy-pasting a curl command from a recent web framework's website and instantly getting a To-Do app. Simple ≠ Easy to Use for Literal Newbies.What Simplicity Actually MeansSimple means fewer moving parts. If you consider a piece of software as a whole mechanism potentially down to assembly instructions (and possibly hardware), how many moving parts does it have? The fewer moving parts it has, the simpler it is.And no, I'm not talking about assembly instructions because I believe the speed of software is above all. I'm talking about them because you need to consider all the parts to tell if it's simple or not. Shoving complexity behind an API does not remove it.Why Moving Parts MatterWhy am I concerned with the amount of moving parts? Because you want to control them. If you think you don't, you are setting yourself up for a failure in the long run. In the short term, sure it is easier to copy-paste the curl command. But then let's meet in 10 years and talk again.Benefits of Fewer Moving PartsEasier DeploymentThe fewer parts, the easier the deployment. Imagine a program that does exactly what you need and it's a self-contained executable that only depends on what the OS is providing. You just copy-paste it and run it. No install, no docker, no package managers. How cool is that?Easier MaintenanceThe fewer parts, the easier the maintenance. Fewer bugs from 3rd party deps. You don't need to report them and wait for the fix. Or deal with their code to fix them yourself. All the bugs are yours. And there is less of them because you have fewer parts.Smaller Attack SurfaceThe fewer parts, the smaller the attack surface. Imagine being hacked via a vulnerability in a huge framework you rely on? Now multiply that by the amount of other dependencies you have. People are paranoid about simply using C, but tbh this makes me even more paranoid.Easier Team ScalingThe fewer parts, the easier to scale the team. Less parts for new people to learn the project and start making meaningful contributions. You need to keep an eye on other people introducing more complexity though.Better Performance (As a Bonus)The fewer parts, the potentially faster it is? I know people will over-fixate on this part, because "oh, there you go, low-level devs are only concerned with performance over convenience." If you felt that way, please reread the above points again.I don't really care about performance. I value comfort and focusing on simplicity provides it. Fewer parts is potentially less code to run, which is a nice bonus imo. Of course performance is a much more complex topic and does not come from just removing code, but it helps a lot.The RealityOf course, we are not living in a perfect world and you can't make your software completely self-contained. But I believe just keeping in mind a mental model of all the moving parts of it makes you aware of the bloat (as we like to describe the software these days).So yeah, next time you hear me talking about Simplicity, hopefully now you understand exactly what I'm talking about.
